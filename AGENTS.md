# Repository instructions

These instructions supplement existing user, environment, and repository instructions; they do not replace them.

## neatHack build companion

- Read `hackathon.md` at the start of a meaningful implementation session. Follow the [official neatHack build-companion skill](https://neatlogs.com/hackathon/skill) requested by the builder.
- Work within this project and respect the user's current scope. Do not implement product features during documentation or initialization tasks.
- At the end of each meaningful implementation session, inspect the actual changes and append a concise dated build-log entry to `hackathon.md`. Use Africa/Lagos (WAT) for dates/times; do not invent historical timestamps.
- Record what changed, observed failures, fixes, tests actually run, evidence, remaining limitations, and the next step. Label retrospective entries and planned work. Keep earlier entries intact; append corrections or updates rather than rewriting history.
- Distinguish installed/configured tools, authenticated verification, and real feature execution. SDK diagnostic fixtures, desktop smoke tests, and Git commits are not evidence of completed agent tasks or captured Entire checkpoints.
- Link only sanitized, shareable evidence. Never copy credentials, environment-file contents, personal data, private prompts/traces, tokens, or customer information into the build log. Keep Entire checkpoint publishing disabled unless the user explicitly authorizes reviewed content for publication.
- Verify current rules and submission requirements at [neatlogs](https://neatlogs.com/hackathon) and [Luma](https://luma.com/s5blr882) before preparing a demo/submission. Mark unavailable or unannounced details pending. Ask only about decisions that cannot be inferred; do not publish team names/handles without the builder choosing them.
- Do not register, publish, deploy, send public posts, or submit without explicit user instruction. The build-companion skill does not establish eligibility or qualify this project.
